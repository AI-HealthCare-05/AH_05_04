# #166 MFDS 전체 키·성분 매핑·순서 확인

상태: 사용자 제공 전체 페이지 2회 관찰 결과 수령. 불완전 키가 있어 전체 유효성 검증 통과는 아님.
2026-09-11. API 인증키는 사용자가 별도 보관하며 저장소·env·채팅에 넣지 않는다.

## 확인한 근거

- [공식 제품 허가정보](https://www.data.go.kr/data/15095677/openapi.do)의 내장 Swagger:
  `getDrugPrdtMcpnDtlInq07`에는 ITEM_SEQ(품목기준코드), MTRAL_CODE(원료코드),
  MTRAL_SN(일련번호), TAMT_SEQ(총량일련번호)가 있다. 명세에서 해당 조합의 전체 고유성,
  변경 시 안정성, 일련번호의 유일성 범위 또는 정렬 보장은 확인하지 못했다.
- API는 pageNo·numOfRows와 응답 totalCount를 제공한다. 해당 Operation의 검색 조건에는
  업체허가번호·제품명·업체명·사업자등록번호가 있고 ITEM_SEQ 필터는 없다.
- [저장소 v2 계약](../contracts/targets/post-mvp-1/catalog-build-v2.md)의 P0 allowlist는
  **기존 합성 인계 계약**의 `MFDS_INGREDIENT_CODE`를 사용한다고 명시한다. 이 이름은
  외부 API 필드명이 아니다. MTRAL_CODE와 동일한 의미·범위라는 운영 매핑 근거는 찾지 못했다.
- 사용자가 제공한 50행×2회 통계는 불완전 후보키 3행을 포함한다. 완전 키에서 중복 그룹
  0건이고 두 샘플의 hash가 같지만 전체 고유성·정렬 의미·공식 매핑 승인을 뜻하지 않는다.

## 현재 판단과 다음 확인

| 항목 | 판단 | 전체 검사에서 얻는 것 | 추가로 필요한 의미 확인 |
| --- | --- | --- | --- |
| 전체 키 | ITEM_SEQ+TAMT_SEQ+MTRAL_SN 후보 유지 | 페이지 경계 포함 중복·다른 내용 충돌·누락 패턴 | 누락 행 처리, 변경 시 키의 의미·안정성 |
| 공식 성분 매핑 | MTRAL_CODE 자동 채택 보류 | 동일 원료코드의 복수 이름, 동일 이름의 복수 코드 | 현재 내부 코드 체계와 원료코드 연결 범위의 명시적 결정 |
| 순서 | 배열 index·숫자 변환 미적용 | 숫자 아닌 순번, 앞자리 0, 숫자 변환 시 충돌 | 두 순번의 범위·우선순위, Catalog 표시 순서와의 관계 |

숫자형 문자열 비율이 100%이거나 두 번 같다는 사실만으로 정렬 계약을 승인하지 않는다.
MFDS 원료코드를 내부 `MFDS_INGREDIENT_CODE`로 사용하는 안은 검토 가능한 선택이지만,
이 검사는 그 결정을 자동으로 만들지 않는다. 이름이 같은 다른 코드를 합치지 않는다.
순서 역시 총량 그룹과 성분 순번의 관계를 확인한 뒤 정한다. 기존 구현의 명시적 order는 유지한다.

## 실행

D-04 작업 디렉터리에서 Python 표준 라이브러리만으로 실행한다. DB·migration·Git 쓰기는 없다.

```bash
python3 -m scripts.rag.audit_mfds_component_keys --live
```

화면에 표시되지 않는 입력란에 Decoding key를 붙여넣고 Enter를 누른다. 결과 JSON만 공유한다.
기본값은 페이지당 100행, 각 순회 최대 1,000페이지, 두 번 순회다. 총페이지가 한도를 넘으면
첫 페이지 후 중단하며 필요한 페이지 수·예상 요청 수를 출력한다. 예산을 확인한 후에만
`--max-pages`로 조정한다(상한 5,000). 자동 재시도·키 저장·인증 URL 출력은 하지 않는다.
진행상황은 stderr에 페이지 수만 표시한다. 원문 행·원료명·코드 값·키는 결과에 출력하지 않는다.

검사 도중 totalCount 변경, 페이지 번호 불일치, 응답 잘림, 빈 페이지, 오류 응답은 실패한다.
모든 선언 페이지를 읽어도 실시간 API의 동일 시점 Snapshot을 입증하지 못하므로 상태는
`FULL_PAGES_OBSERVED_NOT_VERIFIED`다. `observed_candidate_keys_complete_and_unique`는 관찰
데이터 범위의 판정이며, 불완전·중복 행이 있으면 false다. 중복 제거로 결과를 정상화하지 않는다.
두 순회의 hash가 같아도 Source Receipt·공식 성분 승인·장기 안정성 증빙으로 승격하지 않는다.
이 hash는 감사 도구의 관찰 비교값이며 Catalog v2 export/envelope hash가 아니다.

## 검증

전체 감사·기존 소량 probe 합성 테스트 **15 passed**. 페이지 간 중복, 누락, 숫자 변환 충돌,
총건수·페이지 메타데이터 변경, 잘린 페이지, 요청 한도, 이름/코드 관계 통계, 키/URL 비노출을 검사했다.
Ruff·format 통과. 기본 실행은 NOT_RUN이며 인증키 없이 실제 전체 호출을 실행하지 않았다.
애플리케이션 동작·DB 구조는 이번 확인 단계에서 추가 변경하지 않는다. 이전 D-04 전체 CI
결과와 이 도구의 집중 검사 결과는 [D-04 검증 기록](catalog-component-order-166.md)에서 구분한다.

후보키는 **완전한 행 범위에서 관찰상 유일**하다. 전체 126,825행 모두의 키가 검증됐다고
표현하지 않는다. hash의 두 번 일치는 즉시 재조회 관찰 결과이며 장기 안정성 보장은 아니다.

다음 확인은 같은 전체 조회를 반복하는 것보다 다음 의미·처리 규칙을 좁히는 데 집중한다.

1. 빈 31,697행이 어떤 레코드인지 확인한다. 키를 발급하거나 성분 없음으로 확정하지 않고,
   Source 원문 보존과 Catalog Component 적격성 판정을 구분하는 처리안을 검토한다.
   현재 mapper는 필수 값 누락으로 거부한다. 이를 조용히 skip하는 코드 변경은 하지 않았다.
2. MTRAL_CODE를 내부 MFDS_INGREDIENT_CODE에 연결할 범위를 명시적으로 확인한다.
   이름 기반 병합을 도입하지 않고, 기존의 이름 추론 금지 원칙을 그대로 따른다.
3. TAMT_SEQ의 그룹 범위와 MTRAL_SN의 그룹 내 순번 여부를 확인한 뒤 order 규칙을 결정한다.
   숫자라는 이유만으로 전역 order 또는 총량→성분 정렬을 자동 채택하지 않는다.

D-04 반복 성분 참조·DB 보존 전환을 뒷받침하는 실측 근거는 확보됐다. 실제 MFDS 자동 적재의
빈 행 처리·공식 Identity 매핑·순서 의미는 아직 완료되지 않았다. 런타임·DB 변경은 이번
결과 반영에 포함하지 않으며 RLS·Trigger도 추가하지 않는다.

## 빈 행 3건의 공식 상세 대조

2026-09-11 사용자 제공 첫 페이지 조회 결과는 sample_rows=50, blank_component_rows=3이며,
ITEM_SEQ 예시는 아래 세 품목이다. 빈 행은 위 다섯 주요 성분 필드 기준이다. 사용자의 API
집계와 agent가 인증키 없이 브라우저에서 확인한 공식 상세 화면을 구분하여 기록한다.

| ITEM_SEQ | 공식 제품명 | 취소/취하구분 | 원료약품 및 분량 표의 성분 행 수 |
| --- | --- | --- | --- |
| [195700032](https://nedrug.mfds.go.kr/pbp/CCBBB01/getItemDetail?itemSeq=195700032) | 네오마겐산 | 정비취하 | 8 |
| [195800022](https://nedrug.mfds.go.kr/pbp/CCBBB01/getItemDetail?itemSeq=195800022) | 조선무약유황연고 | 정비취하 | 1 |
| [195900019](https://nedrug.mfds.go.kr/pbp/CCBBB01/getItemDetail?itemSeq=195900019) | 순천당아연화연고 | 정비취하 | 1 |

세 화면의 취소/취하일자는 모두 `9999-12-31`로 표시됐다. 표시된 원문 값만 기록하며 실제
미래 취하일이나 유효성 판정 근거로 해석하지 않는다. 행 수는 첨가제 표시를 제외한 해당
표의 행 수이며 공식 Ingredient Identity 또는 API 원료코드 매핑의 증거가 아니다.

**API의 빈 성분 행을 '해당 품목에 성분이 없음'으로 해석할 수 없다는 반례를 확보했다.**
세 사례의 정비취하 상태는 관찰 사실이며 API가 그 상태 때문에 필드를 비운다는 인과관계는
미확정이다. 전체 빈 행 31,697건을 정비취하로 분류하거나 자동 제외하지 않는다.

상세 페이지는 cache URL로 연결됐고 API와 같은 갱신 시점의 Snapshot임을 확인하지 못했다.
웹 표의 순번을 MTRAL_SN으로, 총량 제목을 TAMT_SEQ로 치환하지 않는다. 공개 화면에서
확인한 성분명을 이용해 누락된 API 코드·키를 보충하지 않는다. 원문 보존과 필수 필드 누락
거부를 유지하며 빈 행 반환 조건·내부 Identity 매핑·순번 의미는 별도로 확인한다.

이번 대조에서 agent는 추가 인증 API 호출·운영 코드 변경·DB 변경·외부 메시지 전송을
하지 않았다. 문서 내용과 링크, `git diff --check`를 확인했으며 실행 코드 변경이 없어
테스트를 재실행하지 않았다.
