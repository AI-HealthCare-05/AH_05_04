# 다섯알 디자인 시스템 · 상태별 인터랙션 · 코드 프로토타입

## 문서 목적

이 문서는 디자이너가 사용자 흐름과 상태를 검증하기 위해 만든 코드 프로토타입의 범위와 프론트엔드 핸드오프 규칙을 정의한다.

- 실제 운영 프론트엔드 구현을 대체하지 않는다.
- 실제 API 계약, 인증, 캐싱, 라우팅과 배포 구조는 Frontend CODEOWNER가 결정한다.
- 프로토타입은 비식별 합성 데이터만 사용한다.
- OCR 미확정 값은 일정·가이드의 확정 입력으로 사용하지 않는다.

이 저장소의 `/design-prototype`은 시작부터 Post‑MVP까지 전체 제품 여정과 OCR 품질 실패·필드 검수·키보드·Safe Area 상태를 하나로 통합한다.

전체 화면 범위:

- 처음 시작: 시작, 회원가입, 홈
- 처방·가이드: 업로드, OCR 처리, 결과 검수, 복약 가이드, 챗봇
- 매일 복약: 오늘 일정, 건너뜀 이유, 맞춤 복약 도움, 적용 중 도움, 사용 후기
- 기록·확장: 처방 기록, 복약 리포트, 생활관리, 일반 의약품 확인
- 계정·설정: 메뉴, 내 정보, 건강 프로필, 복약 알림

기존 모바일 UX 구조 보존 규칙:

- 공통 AppShell, 상단 헤더, 하단 `홈·일정·가이드·메뉴` 내비게이션을 유지한다.
- 홈의 히어로·바로가기·복약 흐름 순서를 유지한다.
- 처방전 등록 → OCR 처리 → 결과 확인 → 가이드 순서를 유지한다.
- 가이드가 없을 때 챗봇으로 바로 보내지 않고 등록 필요 안내를 거친다.
- 일정 → 복용 상태 선택 → 건너뜀 이유 → 맞춤 지원 순서를 유지한다.
- 기록·리포트·생활관리·일반 의약품·내 정보·알림·지원 허브와 후기 화면을 제거하지 않는다.

MVP/Post‑MVP 표시는 사용자 화면을 제거하기 위한 필터가 아니라 구현 순서와 API 준비 상태를 나타내는 메타데이터다. 디자인과 사용자 여정에서는 양쪽을 함께 유지한다.

로컬 실행 후 `/design-prototype`에서 확인한다.

```bash
cd frontend
pnpm install
pnpm dev
```

```text
http://localhost:5173/design-prototype
```

팀 개발 환경은 Frontend `http://localhost:5173`, Backend `http://localhost:8000`, Frontend API 주소 `VITE_API_BASE_URL=http://localhost:8000`, Backend CORS 허용 origin `http://localhost:5173`을 기준으로 한다. 이 프로토타입은 API 또는 CORS 설정을 변경하지 않는다.

## 디자인 원칙

1. 파란색은 버튼·링크·선택처럼 사용자가 조작할 수 있는 요소에만 사용한다.
2. 완료·예정·미확인 상태는 색상만으로 구분하지 않고 텍스트와 구조를 함께 사용한다.
3. 한 화면의 강한 채움 색상 블록은 하나를 기본으로 한다.
4. 비활성 버튼은 채우지 않고 회색 테두리와 글자로 표시한다.
5. 의료 안전 관련 정보는 진단이나 복용 승인처럼 표현하지 않는다.
6. Mock, Post-MVP, 공급자 이름, 테스트 상태 전환은 사용자 프레임 안에 표시하지 않는다.

## 데이터 시나리오 구조

화면 컴포넌트와 상태 시나리오에는 약 이름·용량·횟수·기간·복용 시점 값을 직접 고정하지 않는다. `prototypeScenarios.ts`는 상태만 관리하고 실제 값 슬롯은 `prototypeData.ts`에서 별도로 정의한다.

| Scenario | 검증 범위 |
|---|---|
| `empty` | 처방·가이드·복약 기록이 없는 빈 상태 |
| `normal` | 외부 처방 데이터 확인 완료 상태 |
| `low-confidence` | 필드별 OCR 확인 필요 상태 |
| `error` | OCR 품질 미달·재촬영 상태 |
| `taken` | 이번 회차 복용 완료 상태 |
| `skipped` | 이번 회차 미복용 상태 |

상태 시나리오는 빈 화면·저신뢰도·오류·복용 상태처럼 UI 동작만 결정한다. 사용자 이름과 약명·용량·횟수·기간·복용 시점은 독립된 외부 데이터 슬롯으로 주입한다. 로컬 워크벤치에서는 화면 밖의 데이터 슬롯 편집기가 API 역할을 대신하며, 실제 서비스에서는 동일한 입력을 인증된 API 응답으로 교체한다. 사용자 화면에는 시나리오 선택기·데이터 편집기·샘플 진입 버튼을 두지 않는다.

## 컴포넌트 상태

### Button

| 상태 | 표현 | 동작 |
|---|---|---|
| Primary | Action 채움 | 화면의 주요 행동 하나 |
| Secondary | 흰 배경·회색 테두리 | 대체 행동 |
| Ghost | 채움 없음·Action 글자 | 취소·돌아가기·낮은 우선순위 |
| Disabled | 채움 없음·회색 테두리 | 조건 미충족, 클릭 불가 |
| Pressed | 어두운 Action | 터치 피드백 |

### OCR field status

| 상태 | 사용자 의미 | UI 동작 |
|---|---|---|
| 확인됨 | OCR 값이 존재하고 사용자가 원본과 확인 | 중립 배지 |
| 확인 권장 | 값은 있으나 신뢰도 또는 형식상 재확인 권장 | Attention 테두리·배지 |
| 확인 필요 | 핵심 필드 신뢰도 미달 | 필드 강조·직접 수정 제공 |
| 직접 입력 필요 | 값이 누락됨 | 입력창 자동 노출 |

신뢰도 퍼센트는 기본 사용자 행동보다 우선하지 않는다. 약명, 1회량, 하루 횟수, 기간, 복용 시점은 필드 단위로 판단한다.

## OCR 상태별 인터랙션

### 문서 품질 실패

진입 조건 예시:

- 문서 영역을 찾지 못함
- 문서 상·하단이 잘림
- 흔들림·초점·반사로 핵심 필드 판독 불가
- 문서 전체 점수와 별개로 약명·용량 등 핵심 필드를 읽을 수 없음

화면 행동:

1. `다시 촬영하기`
2. `다른 사진 선택하기`
3. `취소하고 돌아가기`

단순 평균 신뢰도만으로 재촬영을 결정하지 않는다. 임계값과 핵심 필드 목록은 OCR·Backend·Frontend 담당자가 공유 계약으로 합의해야 한다.

### 필드 일부 확인 필요

1. 원본 처방전과 구조화 결과를 같은 검수 흐름에서 제공한다.
2. 확인이 필요한 필드에만 배지와 테두리를 표시한다.
3. 미확인 핵심 필드가 있으면 확정 CTA를 비활성화한다.
4. 모든 핵심 필드를 사용자가 확인한 뒤 가이드 생성을 허용한다.

## 챗봇과 모바일 키보드

| 상황 | 레이아웃 규칙 |
|---|---|
| 기본 | 메시지 영역, 입력창, 하단 내비게이션 표시 |
| 키보드 활성화 | 하단 내비게이션 숨김 |
| 입력 중 | 입력창과 전송 버튼을 같은 행에 유지 |
| 긴 입력 | 입력창 최대 높이 이후 입력창 내부 스크롤 |
| 긴 답변 | 메시지 영역만 스크롤, 입력창은 키보드 위 유지 |
| 답변 생성 | 사용자가 최신 메시지 근처에 있을 때만 하단으로 이동 |

프론트엔드 구현에서는 `100dvh`, `env(safe-area-inset-bottom)` 및 필요 시 `visualViewport`를 사용한다. 키보드가 열린 상태에서 질문·전송 버튼·현재 대화가 동시에 보여야 한다.

## 반응형 규칙

| 폭 | 목적 | 콘텐츠 좌우 여백 |
|---:|---|---:|
| 360px | 최소 지원 폭·긴 문자열 검증 | 16px |
| 390px | 기준 디자인 | 20px |
| 412px | 넓은 모바일 검증 | 20px |

- 두 개 CTA가 360px에서 충분한 폭을 확보하지 못하면 세로로 배치한다.
- 약 이름·용량은 안전에 필요한 정보이므로 임의의 말줄임표를 적용하지 않는다.
- 스크롤 콘텐츠의 하단 여백은 고정 내비게이션과 Safe Area의 합보다 커야 한다.
- 모바일 주소창의 축소·확장에도 고정 CTA와 메시지 입력창이 콘텐츠를 가리지 않아야 한다.
- 사용자의 글자 확대를 막지 않는다.

## 프론트엔드 핸드오프 경계

디자인 산출물로 제공하는 것:

- 토큰과 컴포넌트 시각 상태
- 화면별 정상·빈 상태·오류·확인 필요 상태
- 사용자 행동에 따른 화면 전환
- 360·390·412px 및 키보드·Safe Area 규칙
- 의료 안전 문구와 정보 위계

Frontend CODEOWNER가 결정할 것:

- 실제 라우터 구조와 상태 관리 라이브러리
- API 캐싱·재시도·인증 유지
- OCR 상태 코드와 임계값 계약
- 접근성 자동 테스트와 브라우저 호환성
- 디자인 시스템을 실제 서비스 컴포넌트로 채택할 범위
