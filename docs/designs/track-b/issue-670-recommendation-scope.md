# #670 처방 기반 시간 후보 — 착수 검토안

상태: 착수 검토 이력 + Local 구현 검토안. 담당·전문 리뷰 및 공개 승인 대기.

2026-09-17 요청자 선택으로 [PD-670](../../governance/decisions/2026-09-17-explicit-schedule-recommendation-670.md)과
[Proposed 계약](../../contracts/proposed/track-b-explicit-schedule-recommendation-v1.md)에 명시적 식후 간격만 계산하는 첫 구현을 추가했다.
아래 결정 표는 최초 착수 검토 이력이며 일반적인 추천 규칙의 승인으로 해석하지 않는다.
구현 담당: 권가빈. 단일 책임 리뷰어: 송은영 (Backend·데이터·Frontend 소비·안전 경계).
전문 검토: 정현우 (약별 근거·제약·평가), 남한솔 (후보 적용·수정 UX).

## 확인한 구현과 경계

- #669의 [구현 PR #675](https://github.com/AI-HealthCare-05/AH_05_04/pull/675)은 확정 처방 timing_text 원문 표시를 다룬다. 이 검토안에서 병합·배포 완료로 간주하지 않는다. 자유문자열은 검증된 의료 제약 모델이 아니다.
- 생활 시간 API는 요일별 식사 구간·반복 행동·회피 구간을 저장한다. 생활 시간 계약은 Proposed이며 추천 판단을 포함하지 않는다.
- 식사 window의 끝은 실제 식사 종료 시각을 뜻하지 않는다. 여기에 임의 식후 간격을 더하지 않는다.
- 기존 일정 PUT은 사용자 확정 시각을 저장한다. 후보 생성·근거·stale 검증을 제공한다고 간주하지 않는다.
- #422 방향에 따라 저녁 식후=20:00, 모든 식후=30분 등의 일괄 규칙을 만들지 않는다.

## 구현 전에 결정할 항목

| 결정 | 검토 영역 | 필요한 결과 |
| --- | --- | --- |
| 첫 지원 복용 조건 및 근거 출처 | 정현우 전문 검토, 송은영 책임 리뷰 | 조건을 판정할 수 있는 입력·제품 식별·근거 버전 및 중단 기준 |
| 식사 구간과 실제 기준 시각의 차이 | 권가빈·남한솔·정현우 | 필요한 추가 입력과 불규칙/누락 처리 |
| 후보 생성·수정·저장 재검증 | Backend·Frontend | 처방/생활/근거 버전 결속 및 오래된 후보 거부 계약 |
| 후보 설명과 필수 복용 조건 | Frontend·안전 검토 | 추천 이유와 반드시 지킬 조건을 구분한 표시 |

## 권장 구현 순서

1. 위 결정과 전문 검토 근거를 Decision 및 Proposed 계약에 기록한다. 새 URL·DTO·enum은 합의 후 정의한다.
2. Backend에서 확인된 제약만으로 후보를 계산하고 실패·오래된 후보를 검증한다. 기존 일정 저장을 재사용한다.
3. Frontend에 후보·이유·필수 조건을 표시하고 명시적 적용·수정·저장 흐름을 연결한다.
4. 합성 데이터로 정상·정보 부족·충돌·자정·요일 차이·수정·저장 실패·기존 일정 보존과 안전 평가를 검증한다.

사용자 예시의 오후 8시는 화면 예시에만 사용할 수 있고 실행 규칙으로 사용하지 않는다.
사용자 확인 전 자동 저장하지 않으며 기존 일정·처방 횟수·용량을 바꾸지 않는다.
이번 PR에는 Local 전용 후보 계산·적용·저장 재검증을 추가했다. 일반적인 식후 해석·약별 Source 제약·요일별 추천은 미지원이다. 기존 Privacy·Source·의료 안전 공개 게이트는 유지한다.
