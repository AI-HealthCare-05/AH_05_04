## 1. 빈 행: 원문 보존과 Component 적격성을 분리

추천안은 빈 행의 원인을 추정해서 정상 성분으로 바꾸지 않는 것이다.

- 해당 API 응답은 Source 원문으로 보존하되, 성분 행 키·원료코드·분량이 없는 레코드에서
  Component나 Ingredient를 만들지 않는다. ITEM_SEQ는 성분 발생 행의 대체 키가 아니다.
- 검토용 집계에서는 주요 성분 필드가 모두 없는 행과 일부 필드만 없는 행을 구분한다.
  이는 데이터 상태 분류이며 '성분 없음', '취소 품목', '수집 성공' 판정이 아니다.
- 현행 mapper의 필수 값 누락 거부는 유지한다. 원문 수집 성공과 Catalog 구성 완료를
  구분하고, 빈 행을 조용히 버린 뒤 전체 Catalog를 complete로 선언하지 않는다.
- 검증된 일부 제품만 별도 Catalog로 만들려면 먼저 명시적인 입력 대상·제외 근거·완전성
  기준을 승인받아야 한다. 이번에 자동 subset 발행이나 새 상태/DB 테이블을 만들지 않는다.

사용자가 첫 페이지 50행에서 확보한 빈 행 3건의 ITEM_SEQ로 공식 상세 페이지를 대조했다.
세 품목 모두 정비취하로 표시되지만 원료약품 및 분량 표에는 성분이 존재한다.
[품목별 대조 기록](../../testing/mfds-component-key-audit-166.md#빈-행-3건의-공식-상세-대조)을
근거로 빈 API 필드를 성분 없음으로 해석하지 않는다. 다만 API와 화면의 갱신 시점은 다를 수
있으며, 정비취하가 빈 행의 원인인지 또는 전체 31,697행에 적용되는지는 확인되지 않았다.
공급기관 질문에는 이 세 사례를 근거로 정비취하와 반환 조건의 관계를 함께 확인한다.

## 2. 원료코드: 코드 자체를 보존하는 명시적 매핑안

추천 검토안은 이 Operation의 MTRAL_CODE를 문자열 그대로 내부 Ingredient의
canonical_code로 사용하는 공급원 매핑을 정의하는 것이다. 이것은 외부 필드명과 내부
code_system 이름이 원래 같다는 주장이나 승인 완료가 아니다.

검토할 연결안:

- entity_type: INGREDIENT
- code_system: 기존 P0 내부 이름 MFDS_INGREDIENT_CODE
- canonical_code: 확인된 공급원 MTRAL_CODE 원문 문자열
- ingredient_name: 독립 Ingredient 입력의 공급원 이름. 이름은 Identity key가 아님
- 근거: 공급 Operation, 실제 Snapshot/원문 참조, 코드 정의와 적용 범위

기존 합성 인계의 MFDS_INGREDIENT_CODE 이름을 유지할지, 명칭을 분리해야 할지는 Source/Candidate
의미 확인 대상이다. 공급원 범위가 다른 코드와 합치지 않고, 기존 DB 코드의 접두사 변경·
재명명·이름 기준 merge는 수행하지 않는다. 같은 코드가 이후 다른 이름으로 관찰돼도
이름을 통해 새 코드로 치환하지 않는다. 코드 재사용/폐기 정책은 공식 근거를 확인한다.

승인 전에는 현재 map_mfds_component의 독립 Ingredient 입력·expected_material_code 대조를
유지한다. 호출자가 입력을 제공한 것만으로 외부 코드 매핑 승인 또는 Source 승인을 취득하지 않는다.

## 3. 순서: 원본 발생 키와 Catalog 순서를 구분

원본 키는 세 필드의 문자열 조합으로 보존한다. MTRAL_SN 단독이나 API 배열 index를
component_ref로 사용하지 않는다. 순서를 바꿔도 같은 원본 발생 행의 참조는 유지돼야 한다.

검토 가능한 순서안은 **제품별 TAMT_SEQ 그룹 → 그룹 내 MTRAL_SN** 순으로 정렬한 뒤
Catalog용 양의 정수 순서를 부여하는 것이다. 아래 조건을 충족한 후에만 적용을 검토한다.

1. 공급기관 명세 또는 동일 제품의 API/공식 화면 대조로 두 필드의 범위와 순서 의미 확인.
2. 그룹별 중복·원본 키 충돌 검증. 원문은 문자열로 유지하고 숫자 해석 실패/동치 충돌은 거부.
3. Catalog용 순서가 공식 원본 키나 임상적 중요도·복용 순서가 아니라는 의미 명시.
4. 총량 기준이 다른 반복 성분을 합산하거나 하나로 dedupe하지 않음.
5. 총량 그룹의 뜻을 잃는 평탄화가 소비자에게 허용되는지 확인. 불가능하면 현행 v2를
   무리하게 확장하지 않고 그룹 정보를 담는 후속 계약으로 분리.

이는 구현 승인 전 제안이며 현재 order 생성 코드는 추가하지 않았다. 이미 구현한 경로는
명시적으로 주어진 component_order만 받는다. 앞자리 0이 없었던 이번 관찰을 미래 모든
응답의 보장으로 쓰지 않는다.

## 연결 시 기존 제약

제품 목록 Operation과 주성분 상세 Operation은 별개다. 현재 Component는 Product와
Ingredient 모두 같은 Snapshot의 composite FK를 요구한다. 상세 응답을 제품 목록 Snapshot에
속한 것처럼 붙이지 않는다. 세 의미를 정하더라도 실제 Source 입력 구성과 이 제약의 정렬이
필요하다. 이번 의미 확인을 위해 FK를 풀거나 D-02 run을 만들지 않는다.

## 확인 요청에 사용할 질문 — 전송하지 않은 초안

공급기관에 확인할 내용:

1. getDrugPrdtMcpnDtlInq07에서 ITEM_SEQ는 있으나 MTRAL_CODE·TAMT_SEQ·MTRAL_SN·QNT·
   INGD_UNIT_CD가 모두 비는 행은 어떤 조건에서 반환되나요? 해당 행을 성분 데이터 없음으로
   구분할 공식 기준과 원문/상세페이지 대조 방법이 있나요?
2. MTRAL_CODE는 이 서비스에서 어떤 범위의 원료를 식별하나요? 코드 정의 자료와
   코드 변경·폐기·재사용 정책이 있나요? 이름이 같아도 다른 코드는 별도 원료로 유지해야 하나요?
3. TAMT_SEQ는 제품 내 총량 그룹, MTRAL_SN은 그룹 내 성분 순번인가요? 두 필드의 고유성
   범위·정렬 의미와 제품 변경 시 재번호 여부를 확인할 수 있는 명세가 있나요?

팀 검토에 제시할 의견:

빈 행은 Source 원문을 보존하고 Component 입력 미충족으로 다루며, 완전한 Catalog로
승격하지 않는 방향을 제안합니다. 원료는 이름으로 합치지 않고 코드 기준으로 유지하며,
MTRAL_CODE의 내부 Identity 연결과 두 순번의 정렬은 위 공급원 근거를 확인해 확정하고자 합니다.
현재 PR의 반복 성분 참조·DB 보존 전환은 유지하고, 미확정 실제 MFDS 자동 연결은 완료로
표시하지 않는 범위가 적절한지 확인 부탁드립니다.

## 사례 확보 이후 남은 확인

첫 페이지 50행의 빈 행 3건 확보와 공식 화면 대조는 완료했다. 전체 조회를 재실행할 필요는
없다. 빈 행 반환 조건은 공급기관 확인이 남아 있다. 반복 총량 그룹 사례는 추가 확보가
필요할 수 있으므로 조회 범위·요청 수를 먼저 제한한다. 인증키 값은
공유하지 않고 사용자 로컬의 숨김 입력으로만 사용한다. 공급기관의 명세 답변으로 의미가
해소된다면 그 부분에는 추가 인증 조회가 필요 없다.

이번 턴은 공개 자료 조사·제안 문서 작성이며 운영 코드·DB 변경이나 외부 메시지 전송은 없다.
RLS·Trigger·업무용 DB 함수는 추가하지 않는다.
