# Track C 규칙 기반 개인화 지원 전환

## 결정

이번 Track C 인수 범위에서는 RAG, LLM, 실시간 웹 조회와 약별 의료 설명 생성을 사용하지 않는다. 사용자가 직접 선택한 Barrier와 세부 원인을 규칙으로 지원에 연결하고, 필요한 경우 사전 검토된 상담 질문을 선택해 실행계획에 저장한다.

`복약 상태 확인 → Safety → Barrier 하나와 세부 원인 하나 → 지원 최대 2개 → 사용자 선택 → 실행계획 → 사용 기회·사용 여부·도움·부담 후속 확인` 흐름을 목표로 한다. 현재 구현의 6개 Barrier, 서버 소유 라우팅, 정적 Rule·Copy, Plan lifecycle, B→C 무효화는 재사용한다.

## Barrier와 지원

| Barrier | 세부 원인 예시 | 규칙 기반 지원 |
| --- | --- | --- |
| FORGOT | 알림을 못 봄, 미룬 뒤 잊음, 약·회차 혼동 | 일정·기기 알림 확인, 제한된 재알림, 약·회차 일정표 |
| SCHEDULE_OR_TRAVEL | 생활 일정 변경, 약 미지참, 준비 상황 어려움 | 기존 일정 확인, 외출 준비 체크리스트, 준비 계획 |
| INSTRUCTIONS_UNCLEAR | 수량, 횟수, 시간·식사 조건, 약 구분 혼동 | 확인된 처방정보 표시, 상담 질문 선택·저장 |
| NEED_DOUBT | 증상 없음, 효과 미체감, 수치 호전, 필요성 불확실 | 복용 목적·치료 목표에 관한 고정 상담 질문 |
| MEDICATION_CONCERN | 장기 복용, 의존성·내성, 신체 손상, 약 개수, 정보 충돌 | 우려별 고정 상담 질문 |
| ACCESS_OR_COST | 약 부족, 재처방 일정, 방문 어려움, 비용 | 문의 준비 체크리스트 |

세부 원인은 선택형으로만 제공한다. 자유 입력을 AI가 분류하거나 복수 Barrier를 자동 우선순위화하지 않는다. 현재 증상은 Barrier가 아닌 Safety Event로 먼저 처리한다.

2026-09-17.1의 실제 분기 범위는 제한적이다. 복용법·필요성·약 걱정의 세부 원인은 상담 질문을 좁히고, 일정 변경과 약 미소지는 지원을 하나로 좁힌다. 깜빡함·접근/비용의 세부 원인과 외출 준비 어려움은 snapshot에 기록하지만 지원·질문 결과는 바꾸지 않는다. 표의 나머지 세부 지원은 별도 승인 카피와 규칙이 추가된 이후 범위다.

## 실행계획과 후속 확인

상담 질문 ID·문구·적용 범위는 `copy_version`별 JSON 카탈로그에서 관리한다. 서버가 허용한 `question_id`만 저장하며, 질문 문구와 Copy 버전을 Plan snapshot에 보존한다. 재접속 시 활성 버전으로 대체하지 않고 저장 당시 카탈로그로 검증·복원한다. 질문은 의료진에게 자동 전송하지 않는다.

후속 확인은 사용 기회, 실제 사용 여부, 도움 정도, 부담을 각각 기록한다. 기존 v1의 `HELPED`, `NOT_HELPED`, `NOT_SURE` 기록을 추정 변환하지 않는다. 후속 결과가 복약 상태나 Barrier를 자동 변경하지 않는다.

## 안전 경계

확인되지 않은 처방값을 채우지 않는다. 복용량·횟수·간격·식사 조건·중단·재개를 제안하지 않는다. 약별 효능·부작용·상호작용을 생성하지 않는다. 적합한 지원이 없으면 고정 fallback을 사용한다. `PUBLIC_TRACK_C`와 Privacy·의료 안전 공개 게이트는 유지한다.

## 구현 순서

1. Product Decision과 API/DTO/DB 영향 범위를 확정한다.
2. Barrier별 세부 원인·Support·질문·완료 문구를 versioned Rule/Copy로 등록한다.
3. 질문 선택·Plan snapshot·재조회와 후속 v2 계약을 구현한다.
4. Frontend 실행계획·재접속·후속 화면을 연결한다.
5. 6개 Barrier, 0~2개 Offer, stale/replay/소유권, B→C 무효화, Provider 미호출을 합성 fixture로 검증한다.

RAG·LLM 연결(#196)은 이 작업의 선행 조건이 아니며 후속 범위로 유지한다.
