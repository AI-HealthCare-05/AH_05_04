# #458 OCR LLM 전송·동의 연결 검토안

- 상태: Proposed — 가빈님 정책 방향 확인, 은영님 기술·한솔님 UX·최종 문구/버전 확인 및 구현은 미완료
- 확인일: 2026-09-13
- 코드 기준: develop `582d847`
- 구현: 김지혜. Backend/Security 확인: 송은영. Privacy 목적·정책 확인: 권가빈. Frontend 구현·UX: 남한솔.
- #166과 독립. 목적별 저장 기반은 #207 / PR #465를 재사용하며 중복 테이블을 만들지 않는다.

## 사용자 요구와 현행 동작

원본 이미지를 LLM에 보내지 않고 OCR이 인식한 정보에서만 LLM 입력을 구성한다.
OCR → LLM 구조화 → 사용자 검수·수정·직접 입력 흐름을 유지한다.
사용자에게 약품 영역을 새로 지정하게 하는 UI는 요구하지 않는다.

현재 `ocr_runtime/clova_engine.py`는 CLOVA 응답의 전체 `raw_fields`를 구조화기에 전달한다.
`ocr_runtime/llm/structurer.py`는 각 token의 `source_id`, `text`, `center_x`,
`center_y`, `height`, `confidence`를 JSON으로 전송한다. 원본 이미지·object key·사용자 ID는
이 구조화 payload에 포함하지 않는다. CLOVA 이미지 전송과 LLM 텍스트 전송은 서로 다른 경계다.

`ocr_runtime/llm/prompt.py`의 환자명·주소 등 출력 금지는 입력의 외부 전송을 막지 않는다.
OCR 텍스트 자체에도 개인정보가 포함될 수 있으므로 전체 OCR token을 비식별 자료로 간주하지 않는다.

## 전송 최소화 제안 — 승인 전 구현하지 않는 공유 계약

- 전송 후보: OCR에서 관찰된 약품명·함량·용량·단위·횟수·복용 시점·기간 및 구분에 필요한 라벨.
- 처방일: 라벨과 연결된 날짜를 포함할지, 로컬 판독으로 유지할지 정책·정확도 검토 후 결정.
- 제외 목표: 환자명·주민번호·연락처·주소·불필요한 의료기관 정보·문서 전체 자유 텍스트.
- 위치·높이·confidence는 구조화/검증의 실제 필요성을 따져 필드별 유지 근거를 기록한다.
- 로컬에서 허용 입력을 식별하지 못하면 전체 token을 대신 보내지 않는다.
  이때 규칙 기반 결과·직접 입력으로 이어질 상태는 아래 동의 철회와 구분하여 확정한다.
- 정규식으로 일부 식별자만 제거한 결과를 개인정보 제거 완료로 주장하지 않는다.

필터링 시 token ID를 재번호화하면 현재 validator의 `source_id` 및 인접 token 검증이
달라질 수 있다. 전송 허용 ID 집합과 원래 OCR 근거를 함께 검증하고, 전송하지 않은 ID를
LLM이 참조해도 거부하도록 계약·테스트를 설계한다. 규칙 기반 파서가 이미 인식한 최종값만
보내는 방식은 LLM이 OCR 분류 오류를 보완한다는 원래 목적을 충족하는지 별도로 평가한다.

## 동의 검사 위치와 아직 필요한 결정

#207의 목적·상태 결정과 PR #465의 물리 저장 기반은 구분한다.
현재 develop 문서에는 CLOVA 1회·규칙 기반 구조화를 전제한 오래된 설명이 남아 있다.

제안은 기존 `OCR` 목적의 고지 범위를 LLM 구조화까지 명시하고, 필요한 policy version을
책임자가 결정하는 것이다. 새 목적이나 과거 동의의 자동 호환을 임의로 만들지 않는다.

1. Backend 접수 전 및 Worker CLOVA 호출 전 검사는 #207 후속 담당과 연결한다.
2. CLOVA 완료 후 LLM 호출 직전에도 최신 동의·현재 policy·주체를 다시 확인한다.
3. DB 접근은 Worker Service/Repository에 두고 LLM client에 DB 조회 책임을 넣지 않는다.
4. 메시지에 동의 상태를 싣거나 enqueue 시점의 동의를 재사용하지 않는다.
5. 이미 외부로 전송된 요청을 철회로 회수할 수 있다고 주장하지 않는다.

가빈님 답변을 반영한 정책 정본은 [#458 후속 계약](../contracts/proposed/ocr-llm-transfer-458.md)이다.
기존 OCR 목적에 LLM을 명시하되 과거 동의를 자동 확대하지 않고, 변경 안내·policy version 및
재동의를 거친다. OCR 전체 텍스트·이미지는 전송하지 않으며 최소화 불가 시 LLM을 생략한다.
미동의·철회는 정상 성공으로 처리하지 않는다. 철회 후 기존 OCR 결과 검수는 아직 허용을
전제로 구현하지 않으며 직접 입력 경로를 유지한다. 실제 사용자 활성화는 동의·철회·최소화·
Frontend 안내 연결·검증과 기존 외부 게이트 충족 이후다.

남은 결정은 구체 허용 필드·차단 기준·기술적 재검사와 상태 저장(은영), 최종 고지·version·
철회 후 기존 자료 검수 정책(가빈), 안내·재동의·직접 입력 및 결과 상태 화면(한솔)이다.
이 문서의 기술적 제안은 해당 담당자 확인으로 간주하지 않는다.

## Frontend 인계

2026-09-13 남한솔의 MD 검토 후 답변을 후속 계약에 기록했다. 최초 외부 전송 이전 안내,
기존 응답의 LLM 사용 추정 금지, STALE 원인 구분, 독립 직접 입력 저장 경로 확인을 반영한다.
지혜가 Backend 전체를 맡지 않으며 API·동의·철회·감사 변경 범위는 은영과 조율한다.
신규 API 필드·enum·route는 여전히 Proposed다.

호출 경로와 token 최소화의 현행 한계, 합성 테스트 및 남은 인수 시나리오는
[사전 검증 기록](../testing/ocr-transfer-preparation-458.md)에 정리했다.

남한솔에게 외부 OCR 이미지 처리와 외부 LLM OCR 텍스트 처리를 구분한 안내,
목적별 동의 설정 이동, 미동의·철회·LLM 미사용 시 안내 상태를 전달한다.
Frontend 코드를 이 작업에서 대신 수정하지 않는다. UI 문구·전송 범위는 함께 확인한다.

## 구현·검증 순서

1. 위 쟁점과 전송 허용 범위를 책임자와 조율하고 Proposed 계약·인덱스를 갱신한다.
2. 확정 범위의 로컬 token 선택과 LLM payload 경계를 구현한다.
3. #465 기반을 연결해 소유권·목적·policy·철회·조회 실패를 애플리케이션에서 검사한다.
4. 합성 token으로 개인정보 sentinel 비전송, 허용 필드 보존, 숨긴 source ID 거부를 검증한다.
5. CLOVA 대기 중 철회·LLM 직전 조회 실패 시 LLM 호출 0건과 올바른 terminal 상태를 검증한다.
6. OCR/Worker 통합·기존 검수·직접 입력 비퇴행 검사, Frontend 인계 및 담당 리뷰를 연결한다.

신규 RLS·DB Trigger·업무용 DB 함수를 도입하지 않는다. 무결성과 비즈니스 로직은
명시적 Python 검증·transaction과 기존 권한 경계에서 관리한다.
실제 Provider 호출·환경 활성화·배포는 하지 않는다.
