1. 개념

RAG가 뭐야?

비유

AI한테 그냥 물어보면 기억에 의존해서 대답해요. 그런데 우리 약 정보는 AI가 몰라요.
그래서 “대답하기 전에 도서관 먼저 다녀와” 라고 시키는 게 RAG예요.

우리는 여기서 한 발 더

보통 RAG는 “찾아서 답한다”까지입니다. 약은 틀리면 사람이 다치니까 우리는 “찾은 자료를 써도 되는 자료인지 검사하는 문(Evidence Gate)”을 하나 더 두었습니다.

2. 설계 원칙

왜 이렇게 복잡하게 만들어?

코드를 열면 해시, 영수증, 버전이 끝없이 나옵니다. 이유는 딱 세 가지입니다.

① 출처 없으면 답 안 한다

모든 근거 한 조각마다 어느 자료의 몇 번째 문단에서 왔는지를 붙여서 다닙니다. 코드에서는 KnowledgeEvidenceProvenance가 그 꼬리표입니다.

② 모든 단계에 영수증(Receipt)을 남긴다

단계마다 입력을 SHA-256으로 도장 찍어 다음 단계에 넘깁니다. 다음 단계는 “내가 받은 게 진짜 그거 맞아?”를 다시 확인합니다. 안 맞으면 *_RECEIPT_MISMATCH로 멈춥니다.

③ 막히면 조용히 통과시키지 않는다 (fail-closed)

검증에 실패하면 “일단 답은 주자”가 아니라 멈추고 이유를 코드로 남깁니다. VALIDATION_ERROR, DEPENDENCY_ERROR, EVIDENCE_INSUFFICIENT 같은 값들이 그 이유입니다.

한 줄 비유

급식실이랑 같아요. 재료가 어디서 왔는지 모르면 그냥 안 씁니다. 맛보다 안전이 먼저예요.

3. 큰 그림

전체 지도 — 이 한 장이 핵심

RAG 코드는 흩어져 보이지만 실은 공장 라인 하나입니다. 색이 곧 현재 상태입니다.

여기서 꼭 기억할 것

왼쪽 절반(자료 준비)은 진짜로 돌아가고, 오른쪽 절반(찾기·검사)은 “규칙과 시험대”까지 만들어져 있습니다. 그래서 “RAG 다 됐어?”의 정답은 “재료 창고는 완성, 조리대는 설계·검사기 완성, 손님상은 아직”입니다.

4. 파이프라인 ①

공공 API 문을 두드린다 돌아감

비유

모르는 집 문은 안 두드려요. 미리 적어둔 주소만 가고, 갔다 오면 영수증을 받아옵니다.

무슨 코드가 있나

  • source_client/endpoints.py — 어떤 API 주소를 쓸지 목록으로 고정
  • source_client/mfds_client.py — 식약처 API 실제 호출 (약 730줄)
  • source_client/security.py — 사설 IP·이상한 리다이렉트 차단 (SSRF 방어)
  • source_client/decoders.py — 응답 인코딩을 정해진 방식으로만 해석
  • source_client/receipts.py — 호출 결과 영수증 생성
  • source_client/probe.py — 실제 호출 전 “문이 열려 있나” 점검
왜 security.py가 따로 있어?

외부 주소를 불러오는 코드는 공격자가 “우리 내부 서버 주소를 대신 불러줘”라고 속이기 딱 좋은 자리입니다(SSRF). 그래서 DNS 결과가 사설 IP면 아예 거부합니다.

중복 실행 방지

source_ingestion/service.py에 SourceAcquisitionGate가 있습니다. 같은 Source를 동시에 두 번 수집하면 SourceAcquisitionInProgressError로 막습니다. — 같은 자료를 두 번 들여오지 않는다.

5. 파이프라인 ②

원본은 손대지 않고, 지문을 남긴다 돌아감

비유

가져온 자료를 고치지 않고 그대로 보관하고, 겉에 “이 자료의 지문은 이거예요” 스티커(SHA-256)만 붙입니다. 나중에 누가 몰래 바꾸면 지문이 달라져서 바로 들통납니다.

파일하는 일
acquire.py받아온 원본 파일 목록의 무결성 검증
parse.py정규화 입력과 제품별 checksum 준비
normalize.py값을 바꾸지 않고 checksum용 JSON 바이트만 생성
checksums.py원본·제품 레코드 checksum 계산
receipt_validation.py받아온 것과 영수증이 일치하는지 대조
persistence.py원본 보관 → Snapshot 저장 순서 고정
snapshot_lifecycle.pySnapshot 상태 전이 규칙 (523줄)
failure_runs.py실패한 수집도 기록으로 남김
“왜 이름을 예쁘게 정리(NFC) 안 해?”

mfds-product-approval@1 Snapshot checksum은 원문 유니코드를 그대로 보존하는 게 확정 계약입니다. 예쁘게 고치면 지문이 바뀌어서 원본과 대조를 못 하게 됩니다. PD-315 결정문에도 “이 preimage를 변경하지 않는다”라고 못 박혀 있습니다.

DB에 남는 것

backend/app/models/rag_source.py — rag_source, rag_source_endpoint, rag_source_operation, rag_source_snapshot, rag_source_ingestion_run, rag_source_ingestion_artifact, rag_source_snapshot_verification 총 7개 테이블.

6. 파이프라인 ③

약 이름 사전을 만든다 돌아감

비유

“타이레놀”, “아세트아미노펜”, “타이레놀정500밀리그람”… 사람은 같은 약인 걸 알지만 컴퓨터는 몰라요. 그래서 제품 · 성분 · 별명 · 구성을 이어붙인 사전을 만듭니다.

테이블뜻
rag_medication_product제품 (‘타이레놀정500mg’)
rag_medication_ingredient성분 (‘아세트아미노펜’)
rag_medication_alias별명·다른 표기
rag_medication_product_component제품 ↔ 성분 연결과 역할

코드 경계

  • catalog/build.py — 입력을 사전 구조로 조립
  • catalog/validate.py — 규칙 위반 검사
  • catalog/normalize.py — 표기 정규화 규칙(버전 있음)
  • catalog/approval.py — 승인 검증기
  • catalog/export.py — 다음 단계로 넘길 산출물 발행
  • catalog/service.py — 위 넷을 한 작업 경계로 조립
포인트

승인(approval)되지 않은 카탈로그로는 색인을 만들 수 없습니다. catalog/service.py의 CatalogBuildDecision이 거부하면 뒤 단계가 아예 시작되지 않습니다. 발행 envelope는 medication-catalog-v2 / catalog-manifest-envelope-v2입니다.

7. 파이프라인 ④

약 이름 찾기 — 사다리 4칸 계약·순수로직만

비유

이름을 찾을 때 쉬운 방법부터 씁니다. 딱 맞는 이름 → 별명 → 비슷한 철자 → 의미가 비슷한 것. 위 칸에서 찾으면 아래로 안 내려갑니다.

여기가 “계약만”인 이유 — 중요

이 파일(1,397줄)은 결정적 build 로직 + 검색 Port 계약만 가집니다. 공개 함수는 build_candidate_index()와 search_candidate_index() 둘뿐입니다.
주석에 “RAG-07A는 PostgreSQL similarity 또는 ANN 동작을 Python으로 모사하지 않는다”고 적혀 있습니다. 실제 검색은 PostgreSQL이 해야 하고, 이 코드는 그 결과의 순위·출처·영수증을 검증만 합니다. 그 PostgreSQL 어댑터가 아직 없습니다.

8. 파이프라인 ⑤

두 갈래로 찾고 하나로 합친다 합성 어댑터만

비유

친구 둘한테 동시에 시켜요. 한 명은 “단어가 똑같은 것”을 찾고, 다른 한 명은 “뜻이 비슷한 것”을 찾아요. 그다음 둘이 가져온 목록을 공평하게 합쳐서 순위를 다시 매깁니다.

코드에서는

ai_worker/tasks/rag/evidence_retrieval.py(1,194줄)의 retrieve_knowledge_evidence()가 지휘자입니다. 자기가 검색을 하지 않고 세 개의 Port에 시킵니다.

  • QueryBindingVerifierPort — 이 질문이 이 지문(fingerprint)과 맞는지
  • EvidenceSearchPort — LEXICAL / DENSE 단계 검색
  • EvidenceRerankPort — 다시 줄 세우기
“합성 어댑터만”이 무슨 뜻이야?

Port에 꽂을 실제 구현이 evidence_retrieval_synthetic_adapters.py(738줄) 하나뿐이고, 첫 줄에 “Synthetic-only adapters”라고 적혀 있습니다. 즉 진짜 DB를 치는 어댑터가 없습니다. 파일 맨 위 docstring도 “결과는 untrusted retrieval candidates only”라고 선을 그어 둡니다.
PD-315는 합성 점수 방식(weighted-stage-score-v1)이 synthetic 전용이고, Production은 위 그림의 RRF를 쓴다고 확정했습니다.

9. 두 개의 안전장치

영수증, 그리고 비밀로 다루는 질문

① 영수증(Receipt) — 왜 계속 해시를 찍나

비유

요리 단계마다 영수증을 붙여요. 다음 사람이 “네가 쓴 재료가 진짜 그 재료 맞아?”를 영수증으로 확인합니다. 안 맞으면 요리를 버립니다.

실패 코드만 봐도 구조가 보입니다 — QUERY_BINDING_RECEIPT_MISMATCH, SEARCH_RECEIPT_MISMATCH, RERANK_RECEIPT_MISMATCH, ELIGIBILITY_RECEIPT_MISMATCH, RETRIEVAL_RECEIPT_MISMATCH.

모든 참조는 ImmutableArtifactRef(artifact_code, version, content_sha256) 세 쪽 짜리 표로 다닙니다. 이름 + 버전 + 내용 지문이 항상 같이 붙어야 인정됩니다.

② 환자 질문은 비밀로 다룬다

비유

질문지를 봉투에 넣어서 들고 다녀요. 실수로 로그에 찍어도 봉투 겉면만 보여요.

SensitiveText 클래스는 print()하거나 로그에 남기면 <redacted>만 나옵니다. 값을 보려면 .reveal()을 명시적으로 불러야 하고, 한 번 만들면 바꿀 수 없습니다.

대신 검색 단계들끼리는 실제 질문 대신 QueryFingerprint(algorithm, key_version, digest)를 주고받습니다. 질문 원문 없이도 “같은 질문인지”는 확인할 수 있습니다.

멘토님이 물어볼 만한 질문

“왜 점수를 float으로 안 쓰고 문자열로 써?” → 컴퓨터마다 소수점 계산이 미세하게 달라서 해시가 달라집니다. 그래서 CanonicalScore라는 정규화된 십진 문자열로 다닙니다. PD-315는 한 발 더 나가 순위 판정을 기약분수(exact rational)로 하도록 정했습니다.

10. 파이프라인 ⑥

Evidence Gate — 네 개의 검사 검사기만 있음

비유

찾아온 자료를 바로 안 써요. 문 앞에서 네 가지를 물어봅니다. 하나라도 걸리면 못 들어옵니다.

정책은 숫자로 적고, 해시로 못 박는다

VersionedEvidenceGatePolicy는 두 숫자를 가집니다.

  • minimum_supporting_items_per_coverage — 주제 하나당 최소 근거 개수
  • minimum_distinct_source_snapshots_per_coverage — 최소 서로 다른 출처 개수

이 숫자에 충돌 전략·신선도 전략까지 묶어 해시를 만들기 때문에, 기준을 몰래 낮추면 정책 해시가 바뀌어 기록에 남습니다.

여기도 “아직”인 부분

파일 첫 docstring: “No production verifier exists in this slice.” — 자격 검사를 실제로 해 줄 EvidenceEligibilityVerifierPort 구현이 아직 없습니다. 검사 규칙은 완성, 검사를 대신해 줄 권위 기관이 미연결입니다.

11. 파이프라인 ⑦

Runtime Bundle — 도시락 통 DB 계층까지

비유

밥, 반찬, 젓가락을 따로 들고 다니면 하나를 빠뜨려요. 그래서 도시락 통 하나에 다 담고 통에 이름표를 붙입니다. 바꿀 땐 통째로 바꾸고, 잘못되면 통째로 되돌립니다.

테이블뜻
rag_runtime_execution_manifest어떤 코드·모델·프롬프트·파서로 돌릴지 (레시피)
rag_runtime_release_bundle도시락 통 자체 + 통 전체 해시
rag_runtime_bundle_source이 통에 담긴 Source Snapshot 목록과 용도
rag_runtime_environment지금 어느 통이 올라가 있는지 (식탁)
rag_runtime_environment_transition통을 바꾼 이력 — 무엇에서 무엇으로
왜 통째로 묶어?

색인만 새로 바꾸고 규칙은 옛날 걸 쓰면 “설명은 새 자료, 판단은 옛날 규칙”인 위험한 상태가 됩니다. 통째로 묶으면 그런 조합이 아예 생기지 않고, 문제가 나면 이전 통으로 한 번에 되돌릴 수 있습니다.

12. 파이프라인 ⑧ — RAG의 A와 G

증강과 생성 — 근거를 답으로 계약만 · 코드 0건

비유

검사 통과한 자료를 AI한테 그냥 던지지 않아요. “이 자료 안에서만 답해”라고 묶어서 줍니다(증강). 그리고 AI가 답을 써 오면 문장 하나하나가 어느 자료에서 나왔는지 다시 대조합니다(인용 검증).

RAG의 A(Augmented)와 G(Generation)가 여기입니다. 앞 장들이 “재료를 고르는 일”이었다면 이 장은 “요리해서 손님상에 올리는 일”입니다.

정본 그래프에서 이 구간

Chat — … → evidence_gate → generate_answer → claim_citation_validator → release_gate → persist_result

Guide — … → conflict_gate → compose_personalized_guide → claim_citation_validator → release_gate → persist_guide

둘 사이 Citation Finalizer가 CITATION_AUTHORIZATION Guard를 원자적으로 만들고 검증합니다. 이건 Node가 아니라 Application Service 경계입니다.

“계약만”의 근거 — 직접 확인한 것

① evidence_gate.py:280의 docstring이 “Evaluate pre-composer sufficiency, conflict, and freshness signals.” — 게이트가 스스로 “나는 컴포저 직전까지”라고 선을 긋습니다.
② 저장소 전체에 generate_answer·claim_citation_validator·release_gate·compose_personalized_guide 구현 0건.
③ pyproject.toml에 langgraph 의존성 자체가 없습니다. 그래프를 돌릴 런타임이 아직 안 들어왔다는 뜻입니다.

DB는 먼저 깔려 있음 schema-only

  • knowledge_document / knowledge_chunk — 지식 문서와 잘린 조각, 벡터 저장소 키
  • chat_citation — 메시지의 어느 claim_text가 어느 chunk의 cited_text에서 왔는지
  • guide_citation — 가이드용 같은 구조

즉 “인용을 저장할 자리”는 이미 있고, 그 자리를 채울 코드가 없는 상태입니다. docs/ai-pipeline.md가 이 영역을 “Schema-only / Not implemented”로 적어 둔 이유입니다.

말할 때 주의할 용어

정본 계약이 “composer, retrieval, rerank 같은 설명용 단축어를 Node ID로 쓰지 말라”고 명시합니다. 회의에서 “컴포저 단계”라고 부르는 건 괜찮지만, 이슈·PR·평가 산출물에는 generate_answer처럼 정본 이름 그대로 써야 합니다.

13. 파이프라인 ⑨

시험지 세 종류 문제지만 있음

비유

연습문제는 맘껏 풀어요. 정답지는 선생님이 확인해줘요. 진짜 시험지는 봉인해서 금고에 넣어두고, 딱 한 번만 꺼내요. 미리 보면 시험이 의미가 없거든요.

어떤 점수를 재나 — retrieval_metrics.py

  • RECALL_AT_5 — 정답 근거를 상위 5개 안에 몇 %나 담았나
  • PRECISION_AT_5 — 5개 중 몇 개가 진짜 정답인가
  • MRR — 첫 정답이 몇 등에서 나오나
  • NDCG_AT_5 — 정답을 위쪽에 놓았나 (순위 품질)
  • NO_HIT_RATE — 아무것도 못 찾은 비율

여기에 percentile_group_bootstrap_ci()로 95% 신뢰구간까지 냅니다. 한 번 잘 나온 걸 성능이라고 부르지 않겠다는 뜻입니다.

왜 아직 점수가 없어?

채점하려면 실제로 검색을 돌려줄 어댑터가 있어야 합니다. 그게 NOT_IMPLEMENTED라서 baseline 점수 자체가 존재하지 않습니다. 그래서 상태 파일에는 지표 필드를 기록하는 것 자체가 금지돼 있습니다(_reject_unverified_metric_fields). 숫자를 지어내지 못하게 코드가 막아둔 겁니다.

15. 현황

단계별 상태 보드

멘토님께 화면 공유하기 딱 좋은 표입니다. 옆으로 스크롤됩니다.

단계상태근거
① Source 호출구현MFDS client·SSRF 가드·probe·receipt, 테스트 있음
② Snapshot·checksum구현acquire→parse→normalize→checksum→persist→lifecycle 전 구간
③ Catalog구현build·validate·normalize·approval·export·service
④ Candidate Index순수 로직·Port 계약PG/pgvector 어댑터 없음 (의도적으로 Python 모사 금지)
⑤ Retrieval Kernel합성 어댑터만“Synthetic-only” · 결과는 untrusted
⑥ Evidence Gate검사기만“No production verifier exists in this slice.”
⑦ Runtime BundleDB 계층5개 테이블 + repository (#355) · 활성화 흐름 미연결
⑧ 증강·생성 (A·G)계약만정본 Node ID는 확정, 구현 0건 · langgraph 의존성 없음
⑧ 인용 저장 테이블schema-onlychat_citation·guide_citation·knowledge_chunk 존재, 실행 경로 미연결
⑨ Evaluation 실행미실행어댑터 부재로 baseline 없음
Candidate 조회 APIflag OFFPUBLIC_TRACK_F_ENABLED=false → 503 fail-closed
용어 주의 — 멘토님이 정확히 볼 부분

“PR이 머지됐다 ≠ 그 기능이 켜졌다”입니다. 이 프로젝트는 계약 → DB 스키마 → 실제 적재·연결을 따로 진행하고 있어서, 머지된 PR 대부분은 앞 두 계층입니다. 실제로 PUBLIC_TRACK_F_ENABLED는 기본값이 false이고 켜기 전 조건이 문서에 명시돼 있습니다.

16. 현황

지금 막고 있는 것 4개

docs/validation/rag/issue-273/report.md에 기계가 적어 둔 blocking code 그대로입니다.

BLOCKED_BY_RAG_14_ADAPTER

실제 검색 어댑터가 없다. PostgreSQL FTS·trigram·pgvector를 실제로 치고 순위와 영수증을 만들어 줄 구현체. 이게 가장 큰 한 덩어리이고, 이게 생겨야 평가 점수가 처음 나옵니다.

BLOCKED_BY_PROTECTED_RETRIEVAL_RUNNER

보호된 데이터로 평가를 실행할 러너가 없다. 브랜치 368-protected-retrieval-runner가 이 작업 자리입니다.

WAITING_FOR_HOLDOUT_ACCESS_AUTHORIZATION

HOLDOUT 문제를 만들 권한이 아직 승인되지 않았다. 사람이 승인 이벤트를 남겨야 시작할 수 있고, 그전엔 코드가 막습니다.

WAITING_FOR_HOLDOUT_FREEZE

진짜 시험지 봉인이 아직. 현재는 PREPARATION_READY — 준비 끝, 봉인 전.

이 4개의 순서

어댑터(RAG-14) → 러너 → HOLDOUT 권한 승인 → HOLDOUT 작성·봉인 → 실제 채점 → Release 판정. 앞의 두 개는 코드 작업, 뒤의 두 개는 사람 승인이라 병렬로 갈 수 있습니다.

17. 보고용

멘토님께는 이렇게 말하면 됩니다

① 어디까지 왔나
“RAG를 자료 준비 / 찾기 / 검사 / 배포 / 평가 다섯 층으로 나눠 진행 중입니다. 자료 준비층은 실제로 동작합니다 — 식약처 API 호출, SSRF 가드, Snapshot checksum, 약품 Catalog build·승인·export까지 코드와 테스트가 있습니다.”

② 중간층은 어떤 상태인가
“찾기·검사층은 커널과 계약, 그리고 합성 어댑터까지 끝났습니다. Retrieval 커널·Evidence Gate·Candidate Index가 모두 Port 기반이라, 실제 PostgreSQL 어댑터를 꽂으면 바로 돌아가는 구조입니다. 지금은 의도적으로 합성 전용이고 결과를 untrusted로 표시합니다.”

③ 증강·생성은 어디까지
“RAG의 A(증강)와 G(생성)는 정본 LangGraph Node ID까지 확정돼 있습니다 — evidence_gate → generate_answer → claim_citation_validator → release_gate. 인용을 저장할 chat_citation·guide_citation 테이블도 이미 있습니다. 다만 그 Node들의 구현은 아직 0건이고 langgraph 의존성도 안 들어와 있어서, 지금은 ‘설계 확정 + 저장 자리 준비’ 단계입니다.”

④ 남은 것
“평가 문제지는 DEV 60문항과 Gold 20건 승인까지 됐고, HOLDOUT은 준비 완료·봉인 전입니다. 막고 있는 건 네 가지인데 그중 실제 Retrieval 어댑터(RAG-14)가 다음 한 덩어리입니다. 그게 생겨야 첫 baseline 점수가 나옵니다.”

⑤ 안전 관련 한마디
“현재 Release Eligible: false, PUBLIC_TRACK_F_ENABLED=false로 Production은 닫혀 있고, 검증 미완인 상태에서 켜지지 않도록 fail-closed로 잠가 뒀습니다.”

나올 만한 질문 3개와 답

Q. 코드가 이렇게 많은데 왜 아직 못 돌려?
A. 계약과 검증을 먼저 고정하는 순서라서요. 커널은 Port 인터페이스만 알고, 실제 DB 접근 구현은 별도 슬라이스로 뺐습니다. 지금 없는 건 그 구현 한 겹입니다.

Q. 그럼 지금 코드가 맞는지는 어떻게 알아?
A. RAG 관련 테스트 함수가 1,200개 이상 있고, 합성 어댑터로 커널 전 구간을 결정적으로 검증합니다. 그리고 결과에 SUCCEEDED 대신 진단 코드와 영수증을 남기게 해서, 실패 원인이 항상 특정됩니다.

Q. 성능 숫자는?
A. 아직 없습니다. 어댑터가 없어서 실행 자체를 안 했고, 상태 파일에 지표 필드를 적는 것 자체를 코드가 거부합니다. 추정치를 성능으로 보고하지 않는 게 이 트랙의 규칙입니다.
