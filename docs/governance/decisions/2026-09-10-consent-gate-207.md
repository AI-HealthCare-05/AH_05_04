## 목적과 적용 범위

#207은 실제 사용자·환자 데이터를 사용하지 않는 7일 데모 범위에서, 목적별 동의와 철회에 따라 기능 처리를 허용하거나 차단하는 기준을 저장소에 처음 고정한다.

이 Decision은 동의 상태 모델, Backend 접수 전 Gate, Worker 실행 직전 재검사, 오류·상태 매핑, Backend/Worker 판정 fixture의 기준을 정한다. 법무 문구, 외부 Privacy 승인, 실제 사용자 데이터 처리와 Production 공개 승인을 완료했다는 의미가 아니다.

## 결정 1: 동의 목적은 4개로 시작한다

이번 데모 범위의 동의 목적은 다음 4개다.

| purpose | 의미 | 주요 소비 지점 |
| --- | --- | --- |
| `OCR` | 처방전 인식 및 외부 OCR Provider 호출 동의 | OCR 접수, OCR Worker의 CLOVA 호출 직전 |
| `GUIDE` | 복약 가이드 생성 처리 동의 | Guide 접수 또는 Provider 호출 직전 |
| `CHAT` | 챗봇 응답 생성 처리 동의 | Chat 접수 또는 Provider 호출 직전 |
| `NOTIFICATION` | 앱 내부 알림 처리 동의 | 알림 저장·게시·발송 직전 |

회원가입 화면에서는 네 목적을 한 화면에서 함께 받을 수 있지만 저장은 목적별 row로 분리한다. `OCR`, `GUIDE`, `CHAT`, `NOTIFICATION` 미선택은 회원가입을 막지 않는다. 대신 해당 기능을 실행할 때 필요한 목적의 동의가 없으면 그 기능만 차단한다.

한 목적의 철회는 다른 목적의 상태를 변경하지 않는다. 예를 들어 `OCR` 철회는 `GUIDE`, `CHAT`, `NOTIFICATION` row를 수정하지 않는다.

## 결정 2: 저장 상태는 `GRANTED`와 `WITHDRAWN`만 둔다

`user_consent`의 저장 상태는 다음 2개로 제한한다.

| status | 의미 | Gate 판정 |
| --- | --- | --- |
| `GRANTED` | 해당 목적의 현재 policy version에 사용자가 동의함 | policy version이 현재 값이면 허용 |
| `WITHDRAWN` | 사용자가 해당 목적의 동의를 철회함 | 차단 |

동의 row가 없으면 미동의로 판단하고 차단한다. 이번 데모 범위에서는 `NOT_GRANTED`, `POLICY_VERSION_EXPIRED`를 저장 enum으로 추가하지 않는다.

정책 버전은 목적별 현재 version 하나를 사용한다. 동의 시점에 해당 목적의 current policy version을 함께 기록한다. 자동 policy 호환 판정, 일괄 재동의, 과거 version 호환성 판단은 이번 범위에서 제외한다.

## 결정 3: `user_consent`는 목적별 최신 동의 상태 테이블이다

`user_consent`는 사용자별·목적별 현재 동의 상태를 나타낸다. 최소 필드는 다음 기준으로 설계한다.

| 필드 | 기준 |
| --- | --- |
| `id` | row 식별자 |
| `user_id` | 동의 주체. `User`에 속함 |
| `purpose` | `OCR`, `GUIDE`, `CHAT`, `NOTIFICATION` 중 하나 |
| `status` | `GRANTED`, `WITHDRAWN` 중 하나 |
| `policy_version` | 동의 또는 철회 판단에 사용한 목적별 policy version |
| `granted_at` | `GRANTED` 전환 시각 |
| `withdrawn_at` | `WITHDRAWN` 전환 시각, nullable |
| `created_at`, `updated_at` | 감사와 동시성 확인을 위한 기본 시각 |

동일 사용자·동일 목적에 대해 현재 row는 하나만 존재해야 한다. 구현 PR에서는 `user_id + purpose` unique 또는 동등한 current-row 제약을 둔다. 과거 동의 이력을 별도 append-only audit으로 보존할지는 이번 Decision에서 확정하지 않는다.

## 결정 4: Backend와 Worker는 런타임 코드를 공유하지 않고 같은 판정표와 fixture를 공유한다

Backend와 Worker는 서로의 런타임 ORM·Service 코드를 import하지 않는다. 대신 하나의 Decision Table과 동일 Contract Fixture를 기준으로 각각 동의 판정을 구현한다.

최소 fixture는 다음 결과를 고정한다.

| 조건 | 기대 결과 |
| --- | --- |
| row 없음 | 차단 |
| `GRANTED` + 현재 policy version | 허용 |
| `WITHDRAWN` | 차단 |
| 동의 조회 실패 | 차단 |
| 요청 목적과 동의 목적 불일치 | 차단 |
| 계정이 비활성 또는 탈퇴 처리 상태 | 차단 |
| parent resource 소유자와 동의 주체 불일치 | 차단 |

Backend와 Worker의 계약 테스트는 동일 fixture를 읽어 같은 판정 결과를 내야 한다. 판정이 실패하면 Provider 호출은 0건이어야 한다.

## 결정 5: Gate 체크 위치

동의 Gate는 기능별로 다음 지점에서 검사한다.

| 기능 | 접수 전 검사 | 실행 직전 재검사 |
| --- | --- | --- |
| OCR | Backend 접수 전에 `OCR` 동의 확인 | OCR Worker handler에서 CLOVA Provider 호출 직전 재검사 |
| Guide | 현재 동기 경로에서는 Provider 호출 직전 확인. 비동기 접수 연결 후 접수 전 확인 | 비동기 Worker 경로가 연결되면 Provider 호출 직전 재검사 |
| Chat | 현재 동기 경로에서는 Provider 호출 직전 확인. 비동기 접수 연결 후 접수 전 확인 | 비동기 Worker 경로가 연결되면 Provider 호출 직전 재검사 |
| Notification | 이번 데모에서 실제 발송·게시 경로가 연결된 범위의 직전 확인 | 별도 Worker가 생기면 발송 직전 재검사 |

#207은 Guide·Chat의 `202 + Job` 비동기 전환을 새로 구현하지 않는다. 해당 경로가 실제 연결되는 PR에서 동일 Gate를 적용한다.

## 결정 6: WorkerMessage와 Stream에는 동의 상태를 싣지 않는다

`WorkerMessage`, Outbox, Redis Stream envelope에는 `user_id`, 동의 상태, 건강정보, 복약정보를 추가하지 않는다.

OCR Worker는 기존 경계를 유지한다. 동의 주체는 `ocr_job.document_id -> medical_document.uploaded_by` 조인으로 확인한다. Worker는 Backend ORM을 import하지 않고, 기존 `sqlalchemy_ocr_input_repository.py`와 같은 ORM-독립 raw table 조회 패턴으로 필요한 테이블만 선언해 조회한다.

현재 OCR Worker의 외부 호출은 CLOVA OCR 1회이고 구조화는 규칙 기반이다. 따라서 Provider adapter 내부에 별도 DB hook을 두지 않고 Worker handler 진입 후 CLOVA 호출 직전에 동의 상태를 검사한다. 향후 LLM 구조화가 실제 연결되면 안내 문구와 전송 범위를 다시 검토한다.

## 결정 7: 차단과 철회 매핑

동의 Gate 차단은 시점에 따라 다음처럼 처리한다.

| 상황 | 공통 Job | Attempt | 도메인 상태 | 공개 오류/사유 |
| --- | --- | --- | --- | --- |
| Backend 접수 전 미동의 또는 row 없음 | Job 생성하지 않음 | 해당 없음 | 해당 없음 | `CONSENT_REQUIRED` |
| Backend 접수 전 철회 상태 | Job 생성하지 않음 | 해당 없음 | 해당 없음 | `CONSENT_REQUIRED` |
| 접수 후 Worker 실행 전 철회 | `STALE` | `BLOCKED` | OCR은 `FAILED` | OCR `error_code=CONSENT_WITHDRAWN` |
| 동의 조회 실패 | fail-closed | fail-closed | Provider 호출 없음 | 접수 전은 `CONSENT_REQUIRED`, 실행 전은 철회와 같은 차단 계열 |

`AiJobStatus.STALE`와 `AiJobAttemptStatus.BLOCKED`는 이미 존재하는 종료 조합을 사용한다. 새 Worker FailureCode를 만들지 않는다. `STALE` 의미에는 “접수 당시 유효했던 동의가 실행 전에 철회되어 실행 권한의 현재성을 잃음”을 포함한다.

OCR에는 `STALE` 도메인 상태가 없으므로 기존 `OcrStatus.FAILED`와 자유 문자열 `error_code=CONSENT_WITHDRAWN`을 사용한다. `CONSENT_WITHDRAWN`은 Worker 공통 FailureCode가 아니라 OCR 도메인 오류 사유다.

공통 Job 조회는 현재 `STALE`에서 상세 철회 사유를 새 필드로 노출하지 않는다. Frontend는 현재 목적별 동의 상태와 OCR `error_code`를 사용해 일반 시스템 장애와 구분된 안내를 표시한다.

사용자 안내 예시는 다음 수준으로 제한한다.

> 동의가 철회되어 처리가 중단되었습니다. 동의 설정을 확인해 주세요.

## 결정 8: 오류 코드 등록 경계

`CONSENT_REQUIRED`는 접수 전 또는 동기 처리 전 필요한 목적의 동의가 없어 기능 실행을 시작하지 않는 경우의 공통 오류 코드다. 오류 응답은 저장소의 공통 envelope `{code, message, details, trace_id}`를 따른다.

`CONSENT_WITHDRAWN`은 접수 후 실행 직전 철회를 감지한 OCR 도메인 실패 사유다. Backend 공통 오류 응답으로 직접 반환하는 코드가 아니라, OCR Job 결과의 안전한 도메인 `error_code`로 저장한다.

두 값은 승인된 Decision/계약 없이 임의로 다른 문서나 구현에 추가하지 않는다. 구현 PR은 `backend-error-response.md`, OCR Job 상태 계약, 관련 API 문서와 테스트를 같은 변경 흐름에서 정렬한다.

## 결정 9: Frontend와 사용자 흐름

회원가입 시 네 목적을 한 화면에서 받을 수 있으나 목적별로 독립 저장한다. 미선택은 가입 차단 사유가 아니다.

기능 화면에서는 반복 동의창을 계속 띄우지 않는다. 해당 기능이 외부 OCR 또는 AI 처리를 사용할 수 있음을 안내하고, 사용자는 설정의 동의 내역에서 목적별 동의·철회를 변경한다.

현재 OCR 화면 안내는 실제 동작에 맞춰 다음 수준으로 둔다.

> 처방전 인식에는 외부 OCR 서비스가 사용됩니다.

LLM 구조화나 추가 외부 Provider가 실제 연결되면 안내 문구와 목적별 전송 범위를 다시 검토한다.

## 제외

이번 Decision은 다음을 확정하지 않는다.

- 최종 법무 문구와 외부 Privacy 승인
- 실제 사용자 데이터 처리와 Production 공개
- 운영용 보존·삭제 자동화와 Provider 삭제 연동
- 진행 중 외부 요청의 강제 취소·회수와 정교한 철회 경합 제어
- 자동 policy 호환 판정과 일괄 재동의 기능
- 실제 데이터 입력을 막기 위한 별도 화면·검증 기능
- OCR 세부 단계별 별도 동의 목적
- Chat 최근 대화, Citation, RAG Source별 세분 동의 목적
- Guide·Chat 비동기 전환 자체
- Notification 외부 발송 Provider 계약

실제 사용자·환자 데이터를 사용하지 않는다는 전제가 바뀌면 실제 데이터 처리와 외부 전송 범위를 다시 검토한다. 이 Decision만으로 기존 Production·Provider·Safety gate가 해제되거나 외부 승인이 완료된 것으로 처리하지 않는다.

## 최소 검증 기준

구현 PR은 최소한 다음을 검증한다.

1. 가입 시 선택한 목적만 `GRANTED`로 저장되고 미선택이 가입을 막지 않는다.
2. row 없음, `WITHDRAWN`, 동의 조회 실패에서 관련 기능과 Provider 호출이 차단된다.
3. 접수 뒤 철회 시 Worker의 Provider 호출은 0건이고, Attempt는 `BLOCKED`, AI Job은 `STALE`, OCR Job은 `FAILED`가 된다.
4. OCR Job에는 `error_code=CONSENT_WITHDRAWN`이 저장된다.
5. 한 목적의 철회가 다른 목적에 영향을 주지 않는다.
6. 재동의 후 새 요청만 허용하고 과거 차단 Job은 자동 재개하지 않는다.
7. Backend와 Worker가 동일 fixture에서 같은 판정 결과를 반환한다.
8. 다른 사용자의 동의 조회·변경은 차단된다.
9. 동의 상태와 Provider 호출 차단 로그·테스트에는 실제 환자 정보, 처방 원문, Provider 원문 응답이 남지 않는다.

## 후속 작업

- `user_consent` migration/model 및 목적·상태 enum 구현
- Backend 접수 전 Gate 연결: OCR부터 실제 경로에 연결하고 Guide·Chat은 현재 구현 경로와 비동기 전환 경계를 분리
- Worker 실행 직전 재검사 연결: OCR Worker의 CLOVA 호출 직전 검사부터 구현
- Backend/Worker 공통 Contract Fixture 추가
- `CONSENT_REQUIRED` 공통 오류 계약 등록
- OCR `CONSENT_WITHDRAWN` 도메인 실패 계약 등록
- Frontend 동의 내역·철회 UI 및 기능 화면 안내 연결

## 승인 조건

이 Decision은 #207 담당 리뷰어 승인 전까지 Proposed다. 지정 리뷰어가 목적·상태·Gate 차단 의미와 Privacy 경계를 승인한 뒤에만 후속 계약·migration·API/DTO 구현의 기준으로 사용한다.
