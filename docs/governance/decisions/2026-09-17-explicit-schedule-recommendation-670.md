# PD-670 — 확정 처방의 명시적 식후 간격 계산

상태: **요청자 선택에 따른 구현 검토안 / 담당·전문 리뷰 대기 / Local 전용**.
2026-09-17 작업 대화에서 요청자가 추천안을 정해 #677에 구현하고 다른 담당자에게 검토받도록 요청했다.
이는 의료 안전·공유 계약·Production 공개 승인이나 기존 문서 리뷰의 구현 승계를 뜻하지 않는다.
구현 담당: 권가빈. 단일 담당 리뷰어: 송은영 (Backend/API·데이터·Frontend 소비·안전 경계).
전문 검토 증빙: 정현우 (지원 처방 문구·제약·안전 평가), 남한솔 (기준 시각·후보 수정 UX). 아직 미수령.

## 선택

첫 버전은 LLM·약별 추론 없이 **확정 version medication의 완전 일치 문구에 대한 산술 계산**만 한다.
`저녁 식후 30분` + 사용자가 명시한 매일 식사 종료 `19:30`이면 `20:00`을 후보로 반환한다.
30분이나 20시는 기본값이 아니다. `저녁 식후`처럼 간격이 없으면 후보를 반환하지 않는다.
처방 원문 확인과 계산 가능성은 약학적 적절성 승인과 다르다.

- 문구 전체가 `아침/점심/저녁`의 쉼표·가운뎃점 목록 + `식후 N분`인 경우만 지원한다.
  N은 선행 0 없는 1~999 정수이며 실제 처방 문구의 값이다. 이 범위는 parser 범위이지 권장 의료 간격이 아니다.
  부가 지시·조건·범위·식전·취침 전·필요시·격일은 지원하지 않는다.
- 식사 개수가 확정 처방의 하루 횟수와 일치해야 한다. 식사 이름·계산 결과 중복, 입력 누락,
  다음 날로 넘어감은 전부 추천 불가다. 후보 일부만 채우지 않는다.
- `#556` 생활 시간 window는 실제 식사 종료 시각이 아니므로 읽거나 재해석하지 않는다.
  새 입력은 저장하지 않는 이번 일정 편집의 임시 기준 시각이다. 별도 생활 시간 저장 기능·추천 엔진을 만들지 않는다.
- 기존 일정은 매일 같은 시각이므로 사용자가 매일 같은 식사 종료 시각임을 확인해야 한다.
  요일별·불규칙·식사 누락·자정 넘김 지원은 후속 계약으로 남긴다.
- 후보 계산과 적용은 저장하지 않는다. 날짜·기간은 기존 입력으로 남기고 사용자가 저장해야 생성한다.
  식사 종료 시각 수정 시 적용 후보를 지우고 재계산한다. 후보 시각을 직접 수정한 경우 서버 재계산과
  일치해야 저장된다. 사용자가 명시적으로 직접 입력으로 전환하면 기존 수동 저장 계약을 사용한다.
- 저장 시 원문 snapshot ID·parser version·기준 시각·최종 시각을 재검증한다. 처방 활성 version과
  schedule revision은 기존 transaction lock으로 검사한다. 추천 저장은 expected_revision=0만 허용한다.
- Backend `ENV=local`, Frontend DEV만 허용한다. 기존 수동 저장과 공개 게이트는 유지한다.

## 계약 변경과 저장

[Proposed 계약](../../contracts/proposed/track-b-explicit-schedule-recommendation-v1.md)에 새 POST·선택 PUT 필드·오류를 정의한다.
DB migration·새 enum·테이블·Trigger·RLS·외부 Source·Provider 호출은 없다.
후보 발급 레코드 대신 immutable 처방 snapshot과 입력으로 저장 시 재계산한다.
생활 시간 문서를 소비하지 않으므로 생활 시간 revision에 의존하지 않으며, UI 임시 입력 변경이 후보를 무효화한다.
후보가 없는 기존 PUT의 멱등 fingerprint는 기존과 동일하게 유지한다.

## 검토 및 남은 범위

#670 전체 완료를 선언하지 않는다. 약별 Source 기반 제약·일반적인 `식후` 해석·요일별 추천은 미지원이다.
담당 및 전문 검토 후 지원 문법·직접 입력 전환·공개 범위를 결정해야 한다. 문서는 `proposed/`에 유지한다.
[검증 기록](../../validation/track-b/issue-670-recommendation.md)과 테스트를 함께 검토한다.

## 2026-09-17 리뷰 반영 — 후보 조회 잠금 제거

[책임 리뷰어 의견](https://github.com/AI-HealthCare-05/AH_05_04/pull/677#issuecomment-5707643616)에 따라
후보 계산은 행 잠금 없는 SELECT로 활성 version·SELF 소유권·snapshot 무결성을 확인한다.
기존 `is_owned()`는 과거 version도 허용하므로 단순 교체하지 않고 조회의 활성 version 조건을 유지한다.
실제 저장의 `lock_active_owned()`와 revision 검증은 유지하며 API/DTO·오류 의미·공개 범위는 바꾸지 않는다.
