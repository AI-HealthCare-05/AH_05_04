# PD-718 — Track C 규칙 기반 개인화 지원

- 상태: 사용자 방향 확정 / 구현·책임 리뷰 대상 / 공개 승인 아님.

## 결정

이번 Track C 구현은 RAG·LLM·실시간 웹 조회를 선행 조건에서 제거한다. 기존 서버 소유 정적 Rule·Copy와 Plan lifecycle을 확장해 `Barrier → 선택적 세부 이유 → 최대 2개 지원 → 사용자 선택 → 고정 상담 질문 → Plan snapshot`을 제공한다.

새 검색 인프라와 외부 Provider 장애가 복약 지원을 막지 않고, 의료 검토 전 생성 문구가 사용자에게 노출되지 않게 하는 것이 목적이다. 세부 이유는 코드 allowlist이며, 질문 ID·문구·적용 범위는 불변 `copy_version` 카탈로그에 두고 서버가 Plan 생성과 과거 Plan 복원 시 다시 검증한다.

## 선택한 구조

기존 JSONB `action_config_snapshot.parameters`에 세부 이유와 질문 ID를 저장한다. 현재 요구사항은 Plan당 단일 선택과 최대 3개 질문이므로 새 테이블·상태·Provider 추상화를 추가하지 않는다. Rule/Copy는 새 불변 버전으로 올리고 과거 버전을 보존한다.

질문이 필요한 복용법·필요성·약 걱정 지원만 고정 질문을 제공한다. 세부 이유가 있으면 관련 질문만 좁혀 반환하고, 없으면 해당 지원의 일반 질문을 반환한다. 질문 선택은 화면에서 하나 이상 요구하지만 기존 API 소비 호환을 위해 request의 빈 목록은 허용한다.

이번 버전에서 복용법·필요성·약 걱정의 세부 이유는 질문을 좁히고, 일정 변경과 약 미소지는 지원을 하나로 좁힌다. 깜빡함·접근/비용의 세부 이유와 외출 준비 어려움은 기록하되 결과를 추가로 분기하지 않는다. 이 범위는 새 의료 문구나 근거 검토 없이 세부 이유별 행동을 추정하지 않기 위한 단계적 제한이다.

## 안전과 공개

현재 증상은 계속 Safety에서 먼저 처리한다. 복용량·횟수·간격·식사 조건·중단·재개를 결정하거나 약별 의료 설명을 생성하지 않는다. 질문은 의료진에게 자동 전송하지 않는다. 기존 SELF·현재성·멱등성·B→C 무효화와 외부 공개 게이트를 유지한다.

## 검토한 대안

- RAG 검색과 LLM 생성: 승인 자료 수집·인덱싱·평가·인용·실패 처리까지 필요해 이번 일정의 안정적인 선행 조건으로 두지 않는다.
- URL을 프롬프트에 전달하는 방식: 모델이 URL 내용을 읽는다는 보장이 없고 출처 고정·재현·감사 경계를 만들지 못한다.
- 세부 이유와 질문용 새 테이블: 현재 단일 Plan snapshot으로 원자 저장과 과거 복원이 가능해 추가 migration 비용을 정당화하지 못한다.
