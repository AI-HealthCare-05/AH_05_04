## 목적과 적용 범위

B3(#201, PR #402)의 Check-in 생성·정정 서비스에 기존 SYNC_MUTATION 멱등성과
HTTP 경계를 연결한다. 승인된 경로·상태 전이를 유지하며, #202 인계 코멘트의 응답
후보를 DTO와 OpenAPI로 구체화한다. 아래 HTTP 성공 코드·operation ID·응답 필드의
구체화는 본 Draft PR에서 리뷰할 제안이며, 기존 Approved v4에 이미 포함됐다고
해석하지 않는다. 리뷰 전 Current 승격·머지·Production 공개 근거로 사용하지 않는다.

## HTTP·DTO 제안

- `PUT /api/v1/medication-occurrences/{occurrence_id}/check-in`
- OpenAPI `operationId`: `medication-checkin.put`
- 생성·정정·재현 성공: `200`, body는 `{"data": {...}}`.
- 요청 필수: `status=TAKEN|NOT_TAKEN`, 0 이상의 정수 `expected_revision`.
  문자열·boolean revision은 받지 않는다. 최초 생성은 0이다.
- `taken_at`은 생략 또는 null 가능. 값이 있으면 timezone-aware datetime이어야 하며
  `TAKEN`에서만 허용한다. UTC로 정규화한다.
- `reason_code`와 알려지지 않은 요청 필드는 거부한다.
- 응답 data: `checkin_id`, `occurrence_id`(UUID), `status`(3개 저장 상태),
  `taken_at`(nullable UTC datetime), `revision`(정수), `corrected`(revision > 1).
- 사용자 `UNCONFIRMED` 입력은 OpenAPI 허용 enum에 넣지 않되,
  실제 입력 시 승인 오류 `422 CHECKIN_STATUS_NOT_USER_SETTABLE`로 매핑한다.
- 기타 입력 오류는 기존 `422 VALIDATION_FAILED`; 인증은 기존 인증 의존성을 따른다.
- 없는 ID와 타 사용자 소유 ID는 동일 `404 MEDICATION_OCCURRENCE_NOT_FOUND`.
  revision·취소·멱등 충돌은 기존 계약의 409 오류를 재사용한다.
- 오류는 공통 `{code,message,details,trace_id}`. 모든 응답에 기존 no-store·trace 경계를 적용한다.

## 멱등성·원자성

`Idempotency-Key`는 기존 16~255자 형식을 따른다. parent resource는 occurrence ID다.
Fingerprint는 정규화한 요청의 `status`, nullable UTC `taken_at`, `expected_revision`이다.
생략한 `taken_at`과 null, 같은 instant의 서로 다른 timezone 표기는 같은 지문이다.
사용자·operation·occurrence는 기존 unique scope에 포함한다.

SELF parent chain 소유권은 snapshot 재현 전에도 확인한다. revision·현재 occurrence
상태 검사는 mutation callback 안에 두므로 같은 키·같은 지문은 현재 revision이
전진한 뒤에도 최초 성공 status와 **전체 data envelope**를 재현한다. 다른 지문은 409다.

현재 Check-in·Audit·occurrence CLOSED 변경과 암호화 snapshot은 같은 session/transaction에
저장한다. 기존 #311 구현은 cap 초과 시 savepoint rollback으로 모든 mutation을 취소한다.
이 구현은 상위 목표의 “mutation 전 크기 확인”을 새로 구현했다고 주장하지 않는다.
외부 부작용이 없는 DB mutation의 원자적 rollback과 미저장을 검증한다.

## 남은 경계

1. 날짜별 일정 조회: `setup_reason` 단일 선택 우선순위와 `USER_CONFIRMATION_REQUIRED`는
   미승인이다. 이번 PR에서 enum·우선순위·fallback을 추가하지 않고 조회 route도 등록하지 않는다.
2. 일정 PUT/PATCH: 원본 `FinalProject Documents/04_Decision/track-b-adherence-v1.md`
   §3.2는 schedule audit과 time retire를 요구하지만 B1 저장 모델에는 해당 테이블·상태가 없다.
   #202는 신규 migration을 제외한다. 원본과 repository target의 정합화 및 범위 결정 전에는
   audit을 생략한 일정 mutation을 구현하지 않는다.
3. Check-in history는 원본 §3.4의 화면 범위 승인이 필요하고, backlog URL·pagination도
   미확정이다. 둘 다 새 route·응답을 추정하지 않는다.
4. Notification·Reminder는 #203, Frontend는 #138이다.
5. Track C #195의 실제 adapter는 아직 연결되지 않았다. B3의 명시적 no-op을 그대로 주입한다.
   C 활성 ActionPlan 무효화 완료 또는 Track C 공개 가능 상태로 해석하지 않는다.

Issue #202 전체 완료나 자동 종료 대상이 아니다. 책임 리뷰어가 HTTP 구체화를 승인한 뒤
남은 범위를 별도 구현·검증해야 한다. 공통 Privacy 및 Track C/F 공개 gate는 유지한다.
